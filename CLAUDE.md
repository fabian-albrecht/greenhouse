# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What Greenhouse is

Greenhouse is a Kubernetes operator (built with Kubebuilder) plus supporting services that provides a "day 2 operations" platform: it manages a fleet of Kubernetes clusters, deploys operational tooling as Plugins (Helm charts), and provides team-based access control. It extends Kubernetes with CRDs reconciled by controllers and guarded by admission webhooks. The dashboard UI lives in a separate repo ([Juno](https://github.com/cloudoperators/juno)); the plugin catalog lives in [greenhouse-extensions](https://github.com/cloudoperators/greenhouse-extensions).

The Go module path is `github.com/cloudoperators/greenhouse`. The `api/` directory is a **separate nested Go module** (`github.com/cloudoperators/greenhouse/api`) containing only the CRD type definitions, so it can be imported by external consumers without pulling in the operator's dependencies.

## Common commands

Build/test tooling is driven by the `Makefile`; most targets download pinned tool binaries into `bin/` on first use. Run `make help` for the annotated target list.

- `make test` — generates manifests + code, then runs `go test ./...` with envtest (controller-runtime integration tests) **and** the nested `api/` module tests. This is what CI gates on and what `CONTRIBUTING.md` requires before a PR.
- `make lint` — runs `golangci-lint` (config in `.golangci.yaml`, includes `ginkgolinter`) against both the root and `api/` modules.
- `make fmt` — `go fmt` + `goimports -local github.com/cloudoperators/greenhouse` for both modules.
- `make check` — `fmt` + `lint` + `test`.
- `make build` — regenerates code and builds all binaries in `cmd/` into `bin/`.
- `make generate-all` — regenerate everything (deepcopy code, CRD/RBAC/webhook manifests, docs, TypeScript types, license headers). **Run this after changing any type in `api/` or any `+kubebuilder` marker in a controller/webhook.**

Running a single test:
- `go test ./internal/controller/team/... -run TestXxx` for plain Go tests.
- Most controller/webhook suites use **Ginkgo + envtest**; the test binary needs `KUBEBUILDER_ASSETS` set. Easiest is to go through `make test`, or replicate its env: `KUBEBUILDER_ASSETS="$(bin/setup-envtest use 1.36.0 -p path)" go test ./internal/controller/plugin/... -ginkgo.focus "some spec"`.

Mocks (in `pkg/mocks/`) are generated by `make mockery` (runs the `vektra/mockery` Docker image against `.mockery.yaml`) — regenerate rather than hand-editing.

## Local development

Full details in `docs/contribute/local-dev.md`. The dev flow spins up KinD clusters (`greenhouse-admin` + `greenhouse-remote`) via the `greenhousectl` CLI and config in `dev-env/`.

- `make setup` — full local install (operator, dashboard, cors-proxy, sample `demo` org with an onboarded remote cluster, Flux, local OCI registry).
- `make setup-controller-dev` — run controllers locally against an in-cluster webhook server. Set `CONTROLLERS_ONLY=true` in your debugger.
- `make setup-webhook-dev` — run the webhook server locally. Set `WEBHOOK_ONLY=true` in your debugger.
- `make e2e` / `make e2e-local` — Ginkgo e2e suites under `e2e/`, selected by build tag (`SCENARIO=cluster|plugin|...`, see `make list-scenarios`).

The single operator binary (`cmd/greenhouse`) runs in one of three modes selected by env vars (`cmd/greenhouse/main.go`): regular (controllers + webhooks), `WEBHOOK_ONLY=true`, or `CONTROLLERS_ONLY=true`.

## Architecture

### Binaries (`cmd/`)
- `greenhouse` — the operator/manager: registers controllers and webhooks. Controller wiring is in `cmd/greenhouse/controllers.go` (`knownControllers` map), webhook wiring in `cmd/greenhouse/webhooks.go`.
- `greenhousectl` — the CLI (dev-env setup, plugin generate/validate, cluster bootstrap); subcommands in `internal/cmd/`.
- `idproxy`, `cors-proxy`, `service-proxy`, `authz` — standalone supporting services.

### API types (`api/`, nested module)
CRDs are grouped under `greenhouse.sap`. Versioned types live in `api/v1alpha1` and `api/v1alpha2`; shared condition/status machinery is in `api/meta/v1alpha1`. Core kinds: `Organization`, `Team`, `TeamRole`, `TeamRoleBinding`, `Cluster`, `ClusterKubeconfig`, `Plugin`, `PluginDefinition`, `ClusterPluginDefinition`, `PluginPreset`, `Catalog` (full list and versions in `PROJECT`). `zz_generated.deepcopy.go` files are generated — never edit by hand.

### The reconciliation framework (`pkg/lifecycle`) — read this first
Controllers do **not** implement the raw controller-runtime `Reconcile` directly. Instead they implement the `lifecycle.Reconciler` interface (`EnsureCreated`, `EnsureDeleted`, `EnsureSuspended`) and delegate to `lifecycle.Reconcile(...)` from their `Reconcile` method. `pkg/lifecycle/reconcile.go` centralizes:
- finalizer add/remove (default finalizer `greenhouse.sap/cleanup`, overridable via the `FinalizerNamer` interface),
- splitting create/update vs. delete phases,
- status-condition management and a single `status().Patch` at the end of every loop (so controllers mutate conditions on the object and let the framework persist them),
- suspension via the `greenhouse.sap/suspend` annotation and re-reconcile via the `greenhouse.sap/reconcile` annotation.

CR types satisfy the `lifecycle.RuntimeObject` interface (`GetConditions`/`SetCondition`/`RemoveCondition`/`CanBeSuspended`). There is also a lighter `ObjectReconciler`/`ReconcileObject` variant for plain `client.Object`s without status conditions. When adding a controller, follow an existing one (e.g. `internal/controller/team/team_controller.go`): `SetupWithManager(name, mgr)` builds the controller and the `knownControllers` map in `controllers.go` registers it under a string name used by the `--controllers`/`--disabled-controllers` flags.

### Controllers (`internal/controller/<domain>/`)
One subdirectory per domain (`cluster`, `organization`, `plugin`, `plugindefinition`, `team`, `teamrbac`, `catalog`). Larger controllers split logic into a `phases/` subpackage. Plugin/Catalog/PluginDefinition deployment uses **FluxCD** (helm-controller, source-controller, kustomize-controller) resources — the Flux CRD schemes are registered in `main.go` and helpers live in `internal/flux` and `internal/helm`.

### Webhooks (`internal/webhook/v1alpha1`, `v1alpha2`)
Defaulting + validating admission webhooks, one file per kind. Markers here feed `make manifests`.

### Other notable `internal/` packages
`clientutil` (k8s client helpers, env/runtime options), `common` (shared config like `DNSDomain`), `config` (`ManagerConfig`, e.g. per-controller `MaxConcurrentReconciles`), `features` (feature flags read from a ConfigMap — gate new behavior here, see `IsOCIMirroringEnabled`, `IsWorkloadIdentityEnabled`, etc.), `dex`/`scim` (identity), `rbac`, `scim`, `ocimirror`, `test` (envtest/Ginkgo harness used across suites).

## Conventions

- **PR titles must be Conventional Commits** (`<type>(<scope>): <description>`) — CI (`ci-pr-title.yaml`) enforces this and the changelog is generated from them. Allowed scopes are a fixed list in that workflow (per-CRD scopes like `plugins`, `teamrolebindings`, plus `controller`, `webhook`, `lifecycle`, `charts`, `greenhousectl`, `dev-env`, `docs`, `e2e`, etc.). Scope is required.
- **Changing a CRD type or `+kubebuilder` marker requires regeneration** (`make manifests` / `make generate` / `make generate-all`); generated manifests live under `charts/manager/` (CRDs in `charts/manager/crds`, RBAC/webhook templates in `charts/manager/templates`), and the Helm chart is `helmify`'d from them. CI will fail if generated output is stale.
- **License headers** are enforced (REUSE / skywalking-eyes). New files need the SAP Apache-2.0 header; `make license` (or `make generate-all`) fixes them.
- Code should follow the [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments); tests are expected with changes.
- Helm charts live in `charts/` (chart-testing config in `ct.yaml`); the deployable operator chart is `charts/manager`.
